# 📐 Master Finding Schema (v1.0.0)
> **Status:** Active Standard | **Applicable to:** `requirement_gap_analyst`, `requirement_logic_analyst`, `advanced_edge_case_analyzer`, `risk_analyst`, `design_auditor`

---

## 1. 🎯 Purpose & Scope
This schema defines the singular standard structure for all Findings, Gaps, Logic Anomalies, Risks, and Design Mismatches generated by any Agent across the QA Framework.

All templates and reports (`*_Req_Gap_Report.md`, `*_Logic_Anomaly_Report.md`, `*_Risk_Analysis_Report.md`, `*_Edge_Case_Report.md`, `*_Design_Audit_Report.md`) **MUST** strictly adhere to this schema to ensure cross-traceability, linkage, and automated validation.

---

## 2. 🆔 Finding ID Specification

Finding IDs MUST follow the format:
$$\text{[TYPE]-[MODULE]-[NNN]}$$

### Standard TYPE Prefixes:
| TYPE Prefix | Responsible Agent | Finding Category | Example |
|:---:|---|---|---|
| **`GAP`** | `requirement_gap_analyst` | Requirement gap, missing rule, broken traceability between PRD and SRS | `GAP-RID-001` |
| **`LOGIC`** | `requirement_logic_analyst` | Internal contradiction, business impossibility, abnormal state transition | `LOGIC-RID-001` |
| **`EDGE`** | `advanced_edge_case_analyzer` | Extreme boundary scenario, concurrency, race condition, interruption | `EDGE-RID-001` |
| **`BVA`** | `advanced_edge_case_analyzer` | Boundary value analysis for numeric inputs or time thresholds | `BVA-RID-001` |
| **`RISK`** | `risk_analyst` | Technical, financial, security, performance, or operational risk | `RISK-RID-001` |
| **`DES`** | `design_auditor` | UI/UX discrepancy between Wireframe/Design and SRS specifications | `DES-RID-001` |

- **`[MODULE]`**: 3–4 letter uppercase abbreviation representing the business module (e.g., `RID` = In-Trip Ride, `FIN` = Host Financial, `SCH` = Scheduled Trips, `AUTH` = Authentication, `PAY` = Payment).
- **`[NNN]`**: 3-digit sequential number starting from `001` (e.g., `001`, `002`, `015`). Arbitrary numbers (e.g., `1` or `01`) are prohibited.

## 3. 📋 Field Specification

| Field Name | Data Type | Mandatory | Value Constraints | Description & Instructions |
|---|:---:|:---:|---|---|
| **`finding_id`** | String | ✅ Yes | Regex: `^(GAP\|LOGIC\|EDGE\|BVA\|RISK\|DES)-[A-Z0-9]{2,6}-\d{3}$` | Project-wide unique identifier for the finding. |
| **`title`** | String | ✅ Yes | Length: 10 – 120 characters | Concise summary of the nature of the issue. |
| **`type`** | Enum | ✅ Yes | `Ambiguity` \| `Contradiction` \| `Missing Rule` \| `Logic Anomaly` \| `Invalid State Transition` \| `Risk` \| `Edge Case` \| `Design Mismatch` | Classification of the nature of the finding. |
| **`severity`** | Enum | ✅ Yes | `Critical` (P0) \| `High` (P1) \| `Medium` (P2) \| `Low` (P3) | Severity ranking defined per `rules/global_rules.md §3`. |
| **`source_doc`** | String | ✅ Yes | Exact file name in `docs/` | Source document where the issue was identified (e.g., `Rider App FRS.md`). |
| **`location`** | String | ✅ Yes | Section name, Section ID, or line numbers | Precise location within the source document (e.g., `Section 3.5, lines 1771-1800`). |
| **`evidence`** | String | ✅ Yes | Direct quote in quotation marks or `[NOT FOUND in {doc}]` | Verbatim excerpt from source document. **STRICTLY FORBIDDEN to fabricate evidence.** |
| **`explanation`** | String | ✅ Yes | Detailed technical explanation | Root cause explaining why this constitutes a gap or logical anomaly. |
| **`impact`** | String | ✅ Yes | Business and technical impact analysis | Consequences if unaddressed (impact on Developers, Testers, or End-users). |
| **`recommendation`**| String | ⬜ Optional | Proposed resolution or clarification request | Suggested remediation. If technical information is insufficient, leave blank without guessing. |
| **`status`** | Enum | ✅ Yes | `Open` \| `Pending Verification` \| `Confirmed` \| `Rejected` | Current finding lifecycle status. Defaults to `Pending Verification` if awaiting BA review. |

## 4. 📝 Standard Markdown Representation

When rendering findings in reports, Agents MUST adhere to the following Block or Register table formats:

### A. Detailed Block Format:
```markdown
### 📌 [GAP-RID-001]: Missing cancellation handling mechanism after driver confirmed pickup
- **Type**: Missing Rule
- **Severity**: 🔴 Critical (P0)
- **Status**: Pending Verification
- **Location**: `Rider App FRS.md` > Section 3.5 (In-Trip Modifications)

**🔍 Evidence:**
> "Rider can request cancellation during active trip by tapping Cancel button."
> Target FRS: [NOT FOUND handling rule for driver payout when cancelled after pickup]

**⚠️ Impact:**
Driver incurs wasted dispatch effort and partial travel distance without a defined base compensation formula, leading to financial dispute and payment processing exceptions in Stripe.

**💡 Recommendation:**
Add Business Rule: If cancelled post-pickup, apply Minimum Trip Fare or calculate compensation based on actual distance travelled to the cancellation point.
```

### B. Register Table Format:
```markdown
| Finding ID | Title | Type | Severity | Status | Location |
|---|---|---|:---:|:---:|---|
| `GAP-RID-001` | Missing post-pickup cancellation formula | Missing Rule | 🔴 Critical | Pending Verification | Sec 3.5 |
| `LOGIC-RID-002` | Contradictory negative Delta fare handling | Logic Anomaly | 🟠 High | Open | Sec 3.5.2 |
| `RISK-RID-001` | Duplicate charge during pre-auth timeout | Risk (Payment) | 🔴 Critical | Open | Stripe Integration |
```

## 5. 🛑 Quality Control Rules
1. **Missing Requirement ≠ Confirmed Defect:** An omitted requirement in documentation is an open question (Gap/Open item). Without formal confirmation from BA/PO, status MUST be set to `status = Pending Verification`.
2. **Anti-Hallucination:** Strictly prohibited to create a Finding without citing verbatim excerpts from the source document or explicitly indicating the exact section searched where the specification was absent.
